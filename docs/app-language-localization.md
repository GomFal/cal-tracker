# App Language And Localization

This document specifies how app languages work in Cal Tracker and how to add new app languages without creating duplicated language lists.

## Core Rule

There is exactly one source of truth for the app languages accepted by the Flutter app:

```dart
AppLocalizations.supportedLocales
```

`AppLocalizations.supportedLocales` is generated by Flutter gen-l10n from the ARB files configured in:

```text
apps/mobile/l10n.yaml
```

The app must not create any other app-language list.

Do not add:

- `LocaleViewModel.supportedLocales`
- `supportedLocaleCodes`
- hardcoded settings language branches such as `if locale == 'es'`
- hardcoded API language mappings such as `es -> es-ES`
- custom language catalogs such as `AppLocaleCatalog`

If a language is accepted by the app, it must come from the ARB/gen-l10n pipeline and appear in `AppLocalizations.supportedLocales`.

## Current Source Files

Language ARB files live in:

```text
apps/mobile/lib/l10n/app_en.arb
apps/mobile/lib/l10n/app_es.arb
```

Flutter gen-l10n config lives in:

```text
apps/mobile/l10n.yaml
```

Generated localization files live in:

```text
apps/mobile/lib/l10n/generated/
```

The generated files are output files. Do not edit them manually. Update ARB files and run gen-l10n instead.

## Runtime Flow

### 1. Flutter Generates Supported Locales

Flutter reads the ARB files and generates:

```dart
AppLocalizations.supportedLocales
```

This is the only app-language list used by production code.

### 2. MaterialApp Uses The Generated Locale List

`MaterialApp.router` uses:

```dart
supportedLocales: AppLocalizations.supportedLocales
```

This makes the UI support exactly the locales generated from the ARB files.

### 3. LocaleViewModel Stores The Selected Locale

`LocaleViewModel`:

- defaults to `AppLocalizations.supportedLocales.first`
- normalizes saved locale values against `AppLocalizations.supportedLocales`
- exposes the active `Locale`
- exposes `localeTag` as `locale.toLanguageTag()`
- saves selected locale values with `Locale.toLanguageTag()`

`LocaleViewModel` does not own a language list.

### 4. Settings Language Picker Is Dynamic

The settings language picker renders options by iterating:

```dart
AppLocalizations.supportedLocales
```

Each option key is generated from the locale tag:

```dart
language_option_${locale.toLanguageTag()}
```

Each option label comes from that locale's generated localization:

```dart
lookupAppLocalizations(locale).settingsLanguageNativeName
```

This means adding a new ARB locale automatically adds a new language option after gen-l10n runs.

### 5. API Requests Send The UI Locale

`CalTrackerApiClient` accepts an optional `localeTagProvider`.

When present, request headers include:

```http
Accept-Language: <locale tag>
```

The API client does not validate, translate, or map language codes. It sends the locale tag it receives.

Examples:

```text
en
es
pt-BR
fr
de-AT
```

### 6. Backend Builds context.locale From Accept-Language

The backend request context reads:

```ts
locale: c.req.header("accept-language")?.split(",")[0] ?? "en-US"
```

So the backend `context.locale` receives the app UI locale sent by Flutter. If no header exists, the backend keeps its current `en-US` default.

### 7. LLM Prompt Receives context.locale

The nutrition assistant prompt includes:

```text
The user's locale is ${context.locale}
```

This is the app/UI locale context.

Important: this is not the same thing as a meal proposal food phrase language.

## App Locale vs Meal Proposal Food Language

The UI locale and meal proposal food language are separate concepts.

App/UI locale:

- comes from the selected app language
- is sent as `Accept-Language`
- becomes backend `context.locale`
- is visible to the LLM prompt as user locale

Meal proposal food phrase language:

- is inferred by the LLM per food phrase
- belongs in `FoodMention.language`
- must reflect the language of the food phrase, not the app UI locale

Example:

```text
App UI locale: es
User says: "add 200 grams of chicken"
FoodMention.language: en
```

The app language must never be used as a fallback food phrase language for meal proposals.

## Adding A New App Language

To add a new app language, do this:

1. Add a new ARB file under:

   ```text
   apps/mobile/lib/l10n/
   ```

   Example:

   ```text
   apps/mobile/lib/l10n/app_pt.arb
   apps/mobile/lib/l10n/app_pt_BR.arb
   ```

2. Set the ARB locale metadata:

   ```json
   {
     "@@locale": "pt"
   }
   ```

   or:

   ```json
   {
     "@@locale": "pt_BR"
   }
   ```

3. Include all required localization keys.

   The new ARB file must include:

   ```json
   "settingsLanguageNativeName": "<native language name>"
   ```

   Examples:

   ```json
   "settingsLanguageNativeName": "Português"
   ```

   ```json
   "settingsLanguageNativeName": "Português (Brasil)"
   ```

4. Run Flutter gen-l10n:

   ```bash
   cd apps/mobile
   flutter gen-l10n
   ```

5. Run tests:

   ```bash
   cd apps/mobile
   flutter test test/locale_view_model_test.dart test/settings_language_widget_test.dart test/api_client_locale_header_test.dart
   flutter analyze
   ```

6. Do not update any separate language list. If a new language requires editing a production list outside ARB/generated l10n, the implementation is wrong.

## Expected Behavior After Adding A New Language

After adding a valid ARB file and running gen-l10n:

- `AppLocalizations.supportedLocales` includes the new locale.
- `MaterialApp.router` accepts the new locale.
- `LocaleViewModel` can load and save the new locale tag.
- settings automatically renders a new language option.
- the option label comes from `settingsLanguageNativeName` in the new locale.
- API calls send the selected locale tag in `Accept-Language`.
- backend `context.locale` receives that tag.
- the LLM prompt sees that tag as the user's app locale.

No production code should need a new hardcoded language branch.

## Validation Checks

Use these checks after changing localization behavior:

```bash
rg "LocaleViewModel\\.supportedLocales|supportedLocaleCodes|settingsLanguageEnglish|settingsLanguageSpanish|settingsLanguageSubtitle|localeCode ==|setLocaleCode|language_option_en|language_option_es" apps/mobile/lib apps/mobile/test
```

Expected production result:

- no `LocaleViewModel.supportedLocales`
- no `supportedLocaleCodes`
- no hardcoded settings language branches
- no hardcoded production language option keys

This check is allowed to find test assertions for current supported languages, but production code must stay dynamic.

Also check the only production supported-locale assignment:

```bash
rg "supportedLocales\\s*=" apps/mobile/lib apps/mobile/test
```

Expected production result:

```text
apps/mobile/lib/l10n/generated/app_localizations.dart
```

Other references may read `AppLocalizations.supportedLocales`, but they must not assign or define a separate list.

## Maintenance Rules

- ARB files define app language support.
- Generated `AppLocalizations.supportedLocales` is the runtime source of truth.
- Production code may iterate `AppLocalizations.supportedLocales`.
- Production code must not duplicate the supported locale list.
- Production code must not map specific language codes for API headers.
- `Accept-Language` carries app/UI locale only.
- `FoodMention.language` carries detected food phrase language only.
- Generated l10n files are regenerated, not manually edited.
